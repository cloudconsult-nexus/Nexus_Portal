## Roles

Three tiers, ranked (`backend/src/middleware/rbac.js`'s `ROLE_RANK`) —
`requireRole('x')` passes for `x` and everything ranked above it, not just
an exact match:

| Role | Key | Rank |
| --- | --- | --- |
| Global Admin | `global_admin` | 2 |
| Customer Admin | `customer_admin` | 1 |
| User | `user` | 0 |

`can_edit_schedule` is a separate per-person boolean grant, not a role tier
— a User with it passes `requireScheduleAccess` the same as a Customer
Admin+ would, for schedule mutations specifically (see below).

## Write/admin operations (role-gated server-side)

Every role not listed under "Allowed roles" receives an HTTP 403 from the
corresponding endpoint. Every one of these is *also* subject to
organization-subtree scoping on top of the role check — see
`frontend/src/pages/help/ApiGuide.jsx`'s "Organization scoping" section for
that layer; this table is role only.

| Area | Operation | Endpoint | Allowed roles |
| --- | --- | --- | --- |
| organizations | create | `POST /organizations` | Global Admin |
| organizations | update | `PUT /organizations/:id` | Global Admin |
| organizations | delete (soft) | `DELETE /organizations/:id` | Global Admin |
| organizations | restore | `POST /organizations/:id/restore` | Global Admin |
| organizations | logo/favicon upload | `POST /organizations/:id/logo`, `/favicon` | Global Admin |
| people | create | `POST /people` | Customer Admin and above |
| people | update | `PUT /people/:id` | Customer Admin and above |
| people | delete (soft) | `DELETE /people/:id` | Customer Admin and above |
| people | set password directly | `POST /people/:id/set-password` | Global Admin |
| people | link additional organization | `POST /people/:id/organizations` | Customer Admin and above |
| people | unlink additional organization | `DELETE /people/:id/organizations/:orgId` | Customer Admin and above |
| calendars | create | `POST /calendars` | Customer Admin and above |
| calendars | update | `PUT /calendars/:id` | Customer Admin and above |
| calendars | delete | `DELETE /calendars/:id` | Customer Admin and above |
| assignments | create/update/delete/copy | `POST/PUT/DELETE /assignments`, `POST /assignments/copy` | Customer Admin and above, **or** a User with `can_edit_schedule` (`requireScheduleAccess`) |
| auto-schedule | preview/commit | `POST /auto-schedule/preview`, `/commit` | Customer Admin and above, or a User with `can_edit_schedule` |
| shift-swaps | approve/reject | `POST /shift-swaps/:id/approve`, `/reject` | Customer Admin and above, or a User with `can_edit_schedule` |
| contact-changes | approve/reject | `POST /contact-changes/:id/approve`, `/reject` | Customer Admin and above |
| invitations | every route (list/resend/revoke) | `/invitations/*` | Customer Admin and above |
| audit-logs | view | `GET /audit-logs` | Customer Admin and above |
| status-alerts | every route except `GET /active` | `/status-alerts/*` | Global Admin |
| report-mappings | every route (admin CRUD) | `/report-mappings/*` | Global Admin |
| tas-settings | update, logo/favicon upload | `PUT /tas-settings`, `POST /tas-settings/logo`, `/favicon` | Global Admin |

## Open access — authenticated, but no role gate

These have no `requireRole`/`requireScheduleAccess` check — any
authenticated role (including plain User) can call them. Where scoping
applies, it's by organization subtree (see ApiGuide.jsx), not by role.

| Area | Endpoint | Notes |
| --- | --- | --- |
| organizations | `GET /organizations`, `GET /organizations/:id`, `.../effective-branding` | Subtree-scoped |
| people | `GET /people`, `GET /people/:id`, `.../organizations`, `.../organizations/candidates`, `POST /:id/photo` | Subtree-scoped |
| calendars | `GET /calendars`, `GET /calendars/:id` | Subtree-scoped |
| assignments | `GET /assignments` | Subtree-scoped |
| shift-swaps | `GET /shift-swaps`, `POST /` (request), `.../accept`, `.../cancel` | **Not** subtree-scoped — every swap request system-wide (see ApiGuide.jsx callout) |
| contact-changes | `GET /contact-changes`, `POST /` (self-service request) | **Not** subtree-scoped |
| status-alerts | `GET /active` | Not even `requireAuth` — fully public |
| reports | `GET /reports/dashboard-summary`, `/coverage`, `/workload`, `/hierarchy-summary`, `/mappings`, `/mappings/:id/embed` | **Not role-gated at the API**, only subtree-scoped — the "OnCall Reports"/"Reports" *menu items* are Customer-Admin-and-above only (see Menu visibility above), but a User with a valid token can call these endpoints directly and get their own subtree's data. Worth a deliberate decision (add `requireRole('customer_admin')` here, or treat it as intentionally open) rather than leaving it as an unreviewed gap between UI and API. |
| customer-messages | `GET /customer-messages` | Scaffolding only — `{ configured: false }` until `CUSTOMER_MESSAGING_URL` is set |
| report-mappings | `GET /report-mappings/visible` | Filtered per-mapping by that row's own `visible_to_roles`, not a blanket role check |
